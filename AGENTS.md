# Project instructions

## Authority and scope
- Read `IMPLEMENTATION_PLAN.md` before coding and follow the authorized milestone exactly.
- Use `RESEARCH_SPEC.md`, v3 source, and saved results as context; do not assume every historical claim is correct.
- Treat `IMPLEMENTATION_PLAN.md` as read-only. Never edit, rewrite, reorder, or weaken it without explicit user authorization.
- Do not edit this file or reinterpret these instructions to bypass a constraint.
- Implement only work the user has authorized. A plan or coding guideline is not permission to launch experiments.
- Preserve v3 source, archived work, datasets, and existing results unchanged; use the new paths specified in the plan.

## Stop and report problems
- If the plan contains a contradiction or leaves a scientific choice unresolved, stop and flag it.
- If a test fails due to an implementation bug, investigate and fix it within the authorized milestone, then rerun the relevant tests.
- Stop and request user approval if resolving the failure requires changing the experimental protocol, mathematical definitions, scientific assumptions, acceptance criteria, or implementation plan.
- Never bypass failing tests, weaken tolerances, or alter experimental conditions merely to obtain passing results.
- Do not silently substitute an algorithm, change a baseline, relax a tolerance, skip a test, or redefine an experiment.
- Do not change hyperparameters, masks, normalization, precision, update rules, or runtime accounting to obtain a passing result.
- Report the affected milestone, expected behavior, observed behavior, evidence, and decision needed from the user.
- You may recommend a fix, but do not apply a plan-changing fix or continue dependent work before the user decides.
- Preserve diagnostic evidence and valid checkpoints; do not overwrite a failed run or hide its outputs.
- Poor accuracy alone is a valid research outcome, not permission to alter or restart the experiment.

## Simple, efficient implementation
- Prefer straightforward functions and explicit control flow over clever abstractions, inheritance, or generic frameworks.
- Keep functions focused and modules few; avoid speculative features, decorative output, and unrelated cleanup.
- Use descriptive names and the smallest dependency set specified in the plan.
- Avoid redundant forward/backward passes, unnecessary tensor copies, GPU synchronization, and retained computation graphs.
- Keep expensive diagnostics separate from normal training and account for all computation that a timed run performs.
- Never trade scientific correctness or reproducibility for speed; preserve the reference path before optimizing it.

## Documentation and comments
- Every function and method, including helpers and tests, must have a concise docstring.
- Begin each docstring with a plain-language, intuitive explanation of the function's broad purpose.
- Document inputs, outputs/return values, relevant units, tensor shapes, and assumptions; state when nothing is returned.
- Describe important side effects: changed parameters, optimizer state, buffers, RNG, files, or device synchronization.
- Explain meaningful failure conditions and how callers should interpret the result.
- Add enough inline comments to follow the reasoning, especially gradient scaling, detachment, clipping, masks, and timing.
- Explain why non-obvious operations are necessary; avoid comments that merely repeat obvious syntax.
- Keep documentation accurate when code changes; prefer clear explanations over dense jargon or long boilerplate.

## Scientific integrity and reproducibility
- Preserve historical method meanings; give changed conditions distinct names and explicit configuration identities.
- Distinguish zero gradients from skipped optimizer steps, and head-update masks from exact-trunk-gradient masks.
- Follow the plan's seed, data-order, augmentation, BatchNorm, checkpoint, and mask-verification contracts.
- Never use validation/test information for predictor fitting, controller calibration, or online switching outside the approved protocol.
- Label retrospective controls, exploratory results, failed targets, resumed runs, and timing limitations explicitly.
- Do not claim speedup from skipped-backprop counts, unequal-accuracy comparisons, or smoke-test results.

## Verification and handoff
- Make small, reviewable changes and run the milestone's authorized tests before advancing.
- Do not launch full training, downloads, dependency changes, or additional experiments beyond the authorized scope.
- Keep generated artifacts in the designated new output directories; never silently reuse incompatible cached state.
- Report what changed, what checks actually ran, their outcomes, and any remaining limitations.
- Never describe an unrun test as passed or an incomplete milestone as complete.
- Stop at the authorized milestone boundary and provide a concise handoff; do not expand the scope independently.
